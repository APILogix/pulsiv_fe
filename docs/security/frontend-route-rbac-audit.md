## 1. Executive Summary & Role Model Verdict

An exhaustive, code-level investigation of the **Pulsiv.dev (Sentinel)** frontend (`pulsiv_fe`) and backend (`pulse`) repositories was conducted across all routes, navigation menus, layouts, state stores, API clients, Fastify route handlers, middlewares, services, and PostgreSQL schemas.

### Summary Verdict on Proposed Roles

1. **Are the four core customer roles (`owner`, `admin`, `member`, `viewer`) sufficient?**
   - **YES — as the primary organizational role hierarchy.** Every customer-facing page and action in the product cleanly maps to one of these four baseline access tiers when paired with two additive permission bundles (`billing_manager`, `incident_responder`) and explicit project-level access inheritance.
   - **Important Discovery Regarding Existing Schema:** The PostgreSQL database (`pulse/database/primarydbv2/02_types/001_enums_and_domains.sql:62-79`) and backend (`pulse/src/modules/organization/shared/types.ts:24-50`) currently define **7 `org_role` values** (`owner`, `admin`, `developer`, `billing`, `security`, `member`, `viewer`) ranked in a **single linear numeric hierarchy** (`100, 80, 60, 50, 50, 40, 20`) and **5 `project_member_role` values** (`owner`, `admin`, `developer`, `qa`, `viewer`).
   - Because the backend uses a numeric `>=` check (`hasMinRole` / `hasRequiredRole`), the existing 7-role linear model causes severe cross-domain privilege leaks (`developer` and `security` pass `>= billing` checks; `billing` and `security` pass `>= member` checks on engineering resources; `security` (50) is blocked from `/security-events` and `/audit-logs` which require `admin` (80)). Consolidating to the **4 core hierarchical roles (`owner > admin > member > viewer`)** and moving orthogonal capabilities (`billing_manager`, `incident_responder`) out of the linear rank eliminates these privilege leaks.

2. **Are the optional permission bundles (`billing_manager`, `incident_responder`) justified?**
   - **`billing_manager`: YES (Strongly Justified).** Billing operations (`/billing/*`, plan upgrades/downgrades, add-ons, coupons, payment methods, invoices, billing summary, and usage attribution) are completely orthogonal to engineering/observability workflows. Finance or procurement personnel (`viewer` + `billing_manager`) need full billing read/write access without being granted `admin` access to API keys, SDK configs, SSO, or telemetry mutations; conversely, engineering managers (`member` + `billing_manager`) may manage budgets without full org administration.
   - **`incident_responder`: YES (Justified as an Additive Bundle or Default `member` Capability).** Pulsiv.dev has a rich operational incident-response surface (`/:orgSlug/alerts/incidents`, `/:orgSlug/alerts/events`, `/:orgSlug/alerts/silences`, `/:orgSlug/observability/errors`, `/:orgSlug/automation/approvals`, `/:orgSlug/automation/runs`). Granting `incident_responder` allows external NOC/support engineers or on-call contractors (`viewer` + `incident_responder`) to acknowledge/resolve/assign incidents, create maintenance silences, triage error groups, and act on workflow approvals **without** granting ability to modify alert rules, escalation policies, routing rules, connectors, or project settings. (Note: Standard engineering `member`s should either include `incident_responder` permissions by default or be assignable the bundle—see Section 6 for policy options).

3. **Is `platform_admin` required and properly separated?**
   - **YES.** Internal platform operations exist in the backend via `users.is_admin BOOLEAN` and `requireAdmin` middleware (`pulse/src/shared/middleware/auth.ts:195-207`), protecting cross-tenant user administration (`/auth/users/*`), MFA recovery completion, quota increase approval/rejection (`POST /organizations/:orgId/quota-requests/:requestId/approve`), and internal billing reconciliation (`/internal/v1/billing/*`). However, `/:orgSlug/super-admin/billing` in the frontend is currently mounted inside customer organization routes (`/:orgSlug/...`) with **zero `is_admin` guard**, and `POST /organizations/:orgId/quota-requests/:requestId/approve` in `quotas.service.ts:138-144` erroneously checks org `owner` instead of `requireAdmin`. `platform_admin` must be strictly separated from customer org roles.

### 2.2 Backend Authorization Mechanisms (`pulse/src`)

There is **no centralized authorization guard or permission registry** in the backend. Instead, 6 incompatible patterns are used across different modules:

1. **Pattern 1 — Linear Numeric Hierarchy (`organization`, `connectors`, `projects/shared/utils.ts`)**:
   - Defined in `pulse/src/modules/organization/shared/types.ts:42-60`:
     ```ts
     export const ROLE_HIERARCHY: Record<OrgRole, number> = {
       owner: 100, admin: 80, developer: 60, security: 50, billing: 50, member: 40, viewer: 20,
     };
     export function hasMinRole(userRole: OrgRole, requiredRole: OrgRole): boolean {
       return ROLE_HIERARCHY[userRole] >= ROLE_HIERARCHY[requiredRole];
     }
     ```
   - **Flaw**: Comparing orthogonal roles (`billing: 50`, `security: 50`, `developer: 60`) with `>=` grants `developer` and `security` access to `billing` endpoints, and grants `billing` and `security` access to `member` (40) endpoints. Meanwhile, `MembersService.requireMember` (`members.service.ts:36-44`) only rejects `status === 'removed'` and `'suspended'`, permitting `'invited'` and `'locked'` statuses!

2. **Pattern 2 — Membership-Only Middleware (`requireOrgAccess` in `pulse/src/shared/middleware/requireorg.ts:39-62`)**:
   - Used by `alerting` and `connectors`. Queries `SELECT 1 FROM organization_members WHERE organization_id = $1 AND user_id = $2 AND status = 'active'`.
   - **Flaw**: Does not select `role` and performs **zero role checks**. In `alerting`, no service-level role checks exist (except on 2 workspace policy routes), leaving 40+ write/delete endpoints open to `viewer`.

3. **Pattern 3 — Split-Brain Project vs. Org Check (`BaseProjectService.requireProjectAccess` in `pulse/src/modules/projects/shared/base.service.ts:167-201`)**:
   - Branches on the string value of `requiredRole`:
     - If `requiredRole` is `"member" | "billing" | "security"`, it checks `organization_members` (`requireOrganizationAccess`).
     - If `requiredRole` is `"viewer" | "qa" | "developer" | "admin" | "owner"`, it checks **only `project_members`** (`getProjectMemberRole`) and **completely ignores `organization_members`**!
   - **Flaws**:
     - An Org `owner` or `admin` who did not create a project has no row in `project_members` and receives **403 `INSUFFICIENT_PERMISSIONS`** when accessing that project!
     - A user removed or suspended from `organization_members` retains `status = 'active'` in `project_members` and can continue reading/mutating the project and minting API keys!

4. **Pattern 4 — Role Fetched in Context but Never Enforced (`observability`, `ai`, `event-analytics`, `analytics`)**:
   - `observability/context.ts:58` and `ai/repository.ts:132` query `om.role` from `organization_members`, attach it to context, and **never check it**, allowing `viewer` to mutate error groups and consume paid AI credits.

5. **Pattern 5 — Bare `authenticate` Using `req.user.currentOrgId` (`billing`)**:
   - Almost all `/billing/*` routes (`subscriptions`, `invoices`, `payment-methods`, `payments`, `refunds`, `addons`, `coupons`, `audit-logs`, `ai`) only run `preHandler: [authenticate]` and read `req.user.currentOrgId` without checking `organization_members` status or role.

6. **Pattern 6 — Explicit Read/Write/Approve Role Sets (`automation/service.ts:62-97`)**:
   - The `automation` module is the best-structured module in the backend (`READ_ROLES`, `WRITE_ROLES = ['owner', 'admin', 'developer']`, `APPROVE_ROLES = ['owner', 'admin', 'security']`), except for one bug in `ingestEvent` (`service.ts:570`) which calls `requireReadAccess` (`viewer`) instead of `requireWriteAccess`.

### 2.3 Frontend Route & Action Gating (`pulsiv_fe/src`)

- **Router Guards (`pulsiv_fe/src/app/router/route-guards.tsx` & `protected-routes.tsx`)**:
  - `RequireAuth` only checks `isAuthenticated`.
  - `OrgRouteGuard` (`protected-routes.tsx:227-272`) only checks if `:orgSlug` is in `organizations`.
  - **Zero routes in `protected-routes.tsx` check `role`, permissions, or `user.is_admin`.**
- **Sidebar & Navigation (`pulsiv_fe/src/app/navigation/navigation.tsx`, `PrimaryRail.tsx`, `AppDualSidebar.tsx`)**:
  - All navigation items—including `Organization` (`/admin/*`), `Billing` (`/billing/*`), and `Developer` (`/projects`, `/connectors/*`)—are rendered unconditionally for every authenticated user.
- **Component-Level Action Gating**:
  - Across all ~100 page components, only **two places** check the user's role:
    1. `OrgProfilePage.tsx:294, 771, 783` (`me?.role === 'owner'` for the Ownership Transfer panel, though Archive/Restore org buttons at lines `826-843` and Save Profile at line `745` are ungated!).
    2. `OrgSettingsPage.tsx:102, 224, 250, 476` (`me?.role === 'owner'` for the Danger Zone panel).
  - Every other page in the frontend (`TeamPage`, `MemberDetailPage`, `DomainsPage`, `SsoPage`, `ScimPage`, `ProjectSettingsPage`, `ProjectApiKeysPage`, `ProjectMembersPage`, `RemoteConfigPage`, `AlertRulesPage`, `IncidentsPage`, `AutomationWorkflowsPage`, `AutomationApprovalsPage`, `AiSettingsPage`, `PaymentMethodsPage`, `WebhooksPage`, `IntegrationsPage`, etc.) renders all create, edit, approve, revoke, and delete buttons **enabled for all users**, including `viewer`.

## 6. Role Validation Against Actual Product Functionality

In accordance with Section 5 of the Master Prompt, each proposed role and permission bundle is evaluated below against verified Pulsiv.dev product capabilities.

### 6.1 `owner` (Core Customer Role — Rank 4)
- **Purpose**: Ultimate legal, financial, and administrative authority for a customer organization (capped at 1 owned organization per user account via `idx_organizations_one_owned_per_user`, and 1 primary owner per organization via `organizations.owner_user_id`).
- **Owner-Only Operations**:
  1. `organization.delete` — Permanently soft-delete the organization (`DELETE /organizations/:id`, must require Step-Up MFA).
  2. `organization.archive` / `organization.restore` — Archive or restore the organization (`POST /organizations/:id/archive`, `/restore`, must require Step-Up MFA).
  3. `organization.ownership.transfer` — Transfer organization ownership to another active member (`POST /organizations/:id/transfer-ownership`, must require Step-Up MFA).
  4. `members.owner.manage` — Promote/demote or remove an `admin` if policy restricts admin-on-admin removal, and prevent any non-owner from modifying the `owner` membership.
- **Inherited Capabilities**: All `admin`, `member`, `viewer`, `billing_manager`, and `incident_responder` permissions across the organization and **implicit `admin` access to all projects in the organization** (fixing the current split-brain bug where `owner` gets `403` on projects created by others).
- **Denied Actions**: Internal platform administration (`platform.*`, such as approving own quota requests or managing global users/plans).

### 6.2 `admin` (Core Customer Role — Rank 3)
- **Purpose**: Day-to-day organization, security, identity, project, and operational administrator.
- **Allowed Actions**:
  - **Organization & Security Settings**: Read and update organization profile, timezone, security policy (`enforceMfa`, `enforceSso`, `sessionTimeoutMinutes`), data residency, and retention (`organization.read`, `organization.update`, `organization.settings.manage`).
  - **Identity, Domains, SSO & SCIM**: Create, verify, configure auto-join, make primary, and delete verified domains (`domains.read`, `domains.manage`); configure and toggle SAML/OIDC SSO providers (`sso.read`, `sso.manage`); create, rotate, and revoke SCIM tokens (`scim.manage`). *(Fixes the current bug where `admin` gets `403` on all Domain, SSO, and SCIM mutations!)*
  - **Team & Member Management**: View all members and invitations; invite new members (`admin`, `member`, `viewer`, plus optional bundles); resend/revoke invitations; change member roles up to `admin` (`viewer <-> member <-> admin` and bundles); suspend, reactivate, and remove non-owner members (`members.read`, `members.manage`). *(Fixes the current bug where `admin` gets `403` on `PATCH /organizations/:orgId/members/:userId/role`!)*
  - **Audit & Security Monitoring**: View and export organization audit logs (`audit_logs.read`, `audit_logs.export`), view security events (`security_events.read`), view compliance status (`compliance.read`), and request quota increases (`quotas.request`).
  - **Projects, Engineering & Operations**: Full access to create, update, archive, and delete projects (`projects.*`), manage project members, environments, API keys (`api_keys.*`), remote SDK configs (`sdk_config.*`), connectors (`connectors.*`), alerting rules/escalations/templates/routing (`alerts.*`), incidents (`incidents.*`), workflows & approvals (`automation.*`), and AI settings (`ai.*`), with **implicit access to all projects in the organization**.
  - **Billing (Read by default; Write configurable)**: Read billing summary, usage, and quota limits (`billing.read`).
- **Denied Actions**:
  - Cannot delete, archive, or restore the organization (`organization.delete`, `organization.archive`).
  - Cannot transfer organization ownership (`organization.ownership.transfer`).
  - Cannot modify, suspend, or remove the organization `owner`.
  - Cannot approve/reject quota increase requests (`platform.quotas.review`).

### 6.3 `member` (Core Customer Role — Rank 2)
- **Purpose**: Standard engineering/developer role for building, instrumenting, debugging, and operating applications in Pulsiv.dev. *(Replaces and unifies the overlapping legacy `'developer'` (60) and `'member'` (40) roles.)*
- **Allowed Actions**:
  - **Telemetry & Observability**: Read all dashboards, services, SLOs, requests, spans, traces, logs, metrics, profiles, crons, replays, and runtime metrics (`telemetry.read`, `dashboards.read`); create/update shared dashboards and scheduled reports (`dashboards.manage`, `reports.manage`, `slos.manage`).
  - **Error Triage & Incident Operations**: Triage error groups (resolve, ignore, reopen, merge, assign via `errors.triage`), acknowledge and resolve incidents, add incident notes, and manage maintenance silences (`incidents.read`, `incidents.acknowledge`, `incidents.resolve`, `alerts.silence`).
  - **Alerting, Connectors & Workflows**: Create and update project/org alert rules, notification bindings, templates, escalation policies, and routing rules (`alerts.read`, `alerts.manage`); configure and test webhooks and integrations (`connectors.read`, `connectors.manage`, `connectors.audit.read`); create, edit, trigger, and retry automation workflows (`automation.read`, `automation.manage`, `automation.execute`).
  - **Projects, Environments, API Keys & Remote SDK Config**: View projects (`projects.read`), create projects (`projects.create`), manage non-locked project environments (`environments.manage`), view/create/rotate/revoke project ingestion API keys (`api_keys.read`, `api_keys.create`, `api_keys.revoke`), and publish/rollback environment SDK remote configurations (`sdk_config.read`, `sdk_config.manage`) for projects they have access to.
  - **AI Suite**: Use AI Assistant, "Ask AI" telemetry analyzers, and root-cause investigations (`ai.read`, `ai.use`).
  - **Organization Visibility**: View organization basic profile, own membership (`/members/me`), basic team directory (`members.read`), and high-level quota headroom (`usage-limits`).
- **Denied Actions**:
  - Cannot delete or archive projects (`projects.delete`) or unlock/delete locked production environments without project admin privilege.
  - Cannot approve high-risk human-in-the-loop automation approvals (`automation.approve` — reserved for `owner`, `admin`, `incident_responder`).
  - Cannot invite, suspend, remove, or change roles of organization members (`members.manage`).
  - Cannot modify organization settings, MFA/SSO enforcement, data residency/retention, domains, SSO providers, or SCIM tokens (`organization.settings.manage`, `domains.manage`, `sso.manage`, `scim.manage`).
  - Cannot view or export organization security events or privileged audit logs (`security_events.read`, `audit_logs.read`, `audit_logs.export`).
  - Cannot view invoices, payment methods, or mutate billing subscriptions (`billing.read`, `billing.manage`) unless granted the `billing_manager` bundle.

### 6.4 `viewer` (Core Customer Role — Rank 1)
- **Purpose**: Strictly read-only stakeholder, executive, auditor, or guest observer. Viewing data must **never** enable state mutation or paid credit consumption through any UI or API path.
- **Allowed Actions**:
  - Read organization basic profile, own membership (`/members/me`), and project list (`organization.read`, `projects.read`).
  - Read home dashboard, custom dashboards, scheduled reports, and service catalog/topology/SLOs (`dashboards.read`, `reports.read`, `telemetry.read`).
  - Read observability telemetry (requests, traces, logs, metrics, profiles, crons, runtime metrics) and error groups (`telemetry.read`).
  - Read alerting overview, incidents, alert events, rules, escalations, silences, routing rules, and metrics (`alerts.read`, `incidents.read`).
  - Read automation workflows, runs, approvals, templates, and events (`automation.read`).
  - Read AI overview, historical AI investigations, and AI reports (`ai.read`).
  - Manage **only** their own personal account settings (`/account/*`, `/auth/sessions`, `/auth/security`) and personal project alert notification preferences (`account.notifications.manage`).
- **Denied Actions (Must Be Enforced on Both Backend and Frontend)**:
  - **Zero write/delete/execute actions** across all organization and project resources.
  - Cannot resolve, ignore, archive, merge, or assign error groups (`PATCH /observability/errors/:id`, `PATCH /api/v1/errors/groups/:id/*`).
  - Cannot acknowledge, resolve, assign, or comment on incidents (`POST /organizations/:orgId/alerting/incidents/:id/*`).
  - Cannot create, edit, toggle, or delete alert rules, silences, escalations, templates, routing rules, or DLQ items.
  - Cannot publish or rollback SDK remote configurations (`PATCH .../sdk-configs/:configId`).
  - Cannot read or mint project API keys (`api_keys.read`, `api_keys.create`, `api_keys.revoke`).
  - Cannot ingest/trigger automation events (`POST /organizations/:orgId/automation/events`), trigger workflows, or approve/reject runs.
  - Cannot trigger paid LLM / AI analyses (`POST /ai/chat`, `POST /ai/analyze/*`, `POST /ai/jobs`, `POST /observability/:resource/ask`) that burn organization AI credits.
  - Cannot access `/admin/*` settings, SSO, SCIM, domains, audit logs, security events, or `/billing/*` invoices/payment methods/subscriptions.

### 6.5 `billing_manager` (Optional Additive Permission Bundle)
- **Justification**: **Strongly justified.** In SaaS organizations, billing is frequently managed by Finance, FinOps, or Procurement staff (`viewer` + `billing_manager`) or an Engineering Director (`member` + `billing_manager`) who should not hold full `admin` control over SSO/SCIM/API keys.
- **Granted Permissions**:
  - `billing.read`: View billing summary (`GET /organizations/:orgId/billing-summary`), entitlements (`GET /billing/entitlements`), current & daily usage (`GET /billing/usage/*`), invoices (`GET /billing/invoices/*`), payment methods (`GET /billing/payment-methods`), billing add-ons (`GET /billing/addons/*`), and billing audit logs (`GET /billing/audit-logs`).
  - `billing.manage`: Upgrade, downgrade, change, or cancel subscriptions (`POST /billing/subscription/*`), attach/detach add-ons (`POST/DELETE /billing/subscription/addons/*`), add/remove/set-default payment methods (`POST/DELETE /billing/payment-methods/*`), pay open invoices (`POST /billing/invoices/:id/pay`), apply coupons (`POST /billing/coupons/apply`), update tax profile (`PUT /billing/tax-profile`), and submit quota increase requests (`POST /organizations/:orgId/quota-requests`).
- **Denied Actions**:
  - Does **not** grant `member` or `admin` access to projects, API keys, SDK configs, telemetry mutations, alerting, connectors, or member management.
  - Cannot issue arbitrary payment refunds (`POST /billing/payments/:id/refund`, `POST /billing/refunds` — must be restricted to `platform_admin`).

### 6.6 `incident_responder` (Optional Additive Permission Bundle)
- **Justification**: **Justified.** Enables on-call responders, NOC analysts, or support engineers (`viewer` + `incident_responder`) to handle live operational incidents, error triage, alert silences, and human-in-the-loop remediation approvals without granting permission to alter alert rules, delete connectors, or manage project infrastructure.
- **Granted Permissions**:
  - `incidents.read`, `incidents.acknowledge`, `incidents.resolve`: Acknowledge, resolve, reassign, and add timeline notes to incidents (`/organizations/:orgId/alerting/incidents/*`).
  - `alerts.silence`: Create and expire alert maintenance silences (`/organizations/:orgId/alerting/silences/*`) and retry/discard alert DLQ deliveries (`/organizations/:orgId/alerting/dead-letters/*`).
  - `errors.triage`: Resolve, ignore, reopen, merge/unmerge, and assign error groups (`/observability/errors/*`, `/api/v1/errors/groups/*`).
  - `automation.execute`, `automation.approve`: Trigger remediation workflows, retry/cancel workflow runs, and approve/reject pending workflow approval gates (`/organizations/:orgId/automation/runs/*`, `/approvals/*`).
  - `ai.use`: Trigger AI root-cause analysis and "Ask AI" during incident triage.
- **Denied Actions**:
  - Cannot create, edit, or delete alert rules, escalation policies, notification templates, or routing rules (`alerts.manage`).
  - Cannot create, edit, or delete connectors/webhooks (`connectors.manage`) or workflow definitions (`automation.manage`).
  - Cannot create/revoke API keys, publish SDK configs, or modify project/org settings.

### 6.7 `platform_admin` (Internal Platform Role — `users.is_admin === true`)
- **Justification**: **Essential and must be strictly isolated from customer RBAC.**
- **Granted Permissions (`platform.*`)**:
  - `platform.users.manage`: List/inspect all users across tenants, lock/unlock, suspend/unsuspend, restore users, revoke sessions, force password resets, and view user audit events (`/auth/users/*`).
  - `platform.quotas.review`: Approve or reject customer organization quota increase requests (`POST /organizations/:orgId/quota-requests/:requestId/approve` and `/reject`).
  - `platform.billing.manage`: Manage global billing plan catalog, issue customer payment refunds (`POST /billing/payments/:id/refund`, `POST /billing/refunds`), issue credit notes (`POST /billing/credit-notes`), and view internal billing state.
  - `platform.system.read`: View global system health and ClickHouse/Kafka ingestion lag (`GET /analytics/v2/system/health`, `GET /api/v1/ingest/dlq`).
- **Isolation Rules**:
  - Never assignable via customer invitation, member role update, or SCIM provisioning.
  - Platform admin UI routes must live under `/platform/*` (not `/:orgSlug/super-admin/*`) and be guarded by `<RequirePlatformAdmin>` on the frontend and `requireAdmin` on the backend.

### 6.8 Unresolved Policy Decisions for Product/Security Sign-Off
1. **Should `admin` include `billing.manage` by default, or only `billing.read`?**
   - *Recommendation*: Grant `admin` `billing.read` by default and require either `owner` or the explicit `billing_manager` bundle for `billing.manage` (subscription changes, payment method mutations). This preserves least privilege while allowing owners to delegate billing to specific admins or finance users.
2. **Should standard `member`s include `incident_responder` permissions by default?**
   - *Recommendation*: Grant `member`s incident acknowledge/resolve (`incidents.acknowledge`, `incidents.resolve`), error triage (`errors.triage`), and alert silence (`alerts.silence`) by default (since developers on-call need these daily), while reserving high-risk automation approval (`automation.approve`) for `owner`, `admin`, and explicit `incident_responder` bundle holders. The `incident_responder` bundle can also be attached to a `viewer` for dedicated NOC/support responders.
3. **Should project access default to Organization-Wide (`member`/`viewer` see all projects) or Explicit Project Membership (`project_members`)?**
   - *Recommendation*: `owner` and `admin` must always have implicit full access to all projects in the organization. For `member` and `viewer`, support an organization-level setting (`defaultProjectAccess: 'all' | 'explicit'`, defaulting to `'all'` so existing org-wide dashboards and observability views work seamlessly, with optional project-level overrides in `project_members`).

## 8. Verified Security Vulnerabilities, Gaps & Evidence

Below is the consolidated inventory of verified security vulnerabilities discovered during the audit, ordered by severity.

### Critical Severity (P0)

1. **[VULN-CRIT-01] Cross-Tenant IDOR on Billing Entitlements (`pulse/src/modules/billing/entitlements/controller.ts:10-16`)**
   - **Evidence**: `resolveOrgId(request)` reads `request.headers['x-org-id'] ?? req.user?.currentOrgId`. `entitlementsRoutes` (`routes.ts:15-19`) only uses `preHandler: [authenticate]` and calls `entitlementsService.getEffectiveEntitlements(orgId)` directly without checking `organization_members`.
   - **Impact**: Any authenticated user can enumerate feature entitlements and plan limits of any tenant organization by supplying `x-org-id: <target-org-uuid>`.

2. **[VULN-CRIT-02] Cross-Tenant Cache Poisoning / IDOR in `SdkConfigService.resolveForSdk` (`pulse/src/modules/organization/sdk-config/sdk-config.service.ts:230-240`)**
   - **Evidence**: `resolveForSdk(orgId, userId, query)` verifies `this.requireMember(orgId, userId)`, then immediately checks `sdkConfigCache.get(sdkConfigCacheKey(query.environmentId))` (keyed **only** by `environmentId`, without `orgId`) and returns the cached object before `this.repo.resolveForEnvironment(orgId, query.environmentId)` can verify that `environmentId` belongs to `orgId`.
   - **Impact**: Any authenticated user in their own organization can read another tenant's cached SDK remote configuration by passing the victim's `environmentId`.

3. **[VULN-CRIT-03] Complete Absence of Membership & Role Checks Across `/billing/*` (`pulse/src/modules/billing/**`)**
   - **Evidence**: `subscriptions`, `invoices`, `payment-methods`, `payments`, `refunds`, `addons`, `coupons`, `audit-logs`, and `ai` routes only use `preHandler: [authenticate]` and read `req.user.currentOrgId`. Furthermore, `POST /billing/subscription/change-plan` (`subscriptions/service.ts:122-177`) directly updates `organization_subscriptions.plan_id` in PostgreSQL without payment provider checkout verification, and `POST /billing/payments/:paymentId/refund` / `POST /billing/refunds` (`payments/service.ts:32-49`) marks payments as refunded with zero role or `requireAdmin` checks.
   - **Impact**: Any `viewer` (or removed/suspended org member whose `users.current_org_id` was never cleared) can upgrade/downgrade/cancel subscriptions, add/delete payment methods, apply coupons, or issue payment refunds.

4. **[VULN-CRIT-04] Ghost Project & API Key Access After Org Member Removal + Split-Brain `requireProjectAccess` (`pulse/src/modules/projects/shared/base.service.ts:167-201` & `organization/members/members.repository.ts:119-133`)**
   - **Evidence**:
     - `MembersRepository.removeMember` and `suspendMember` only update `organization_members` and never revoke `project_members` rows or clear `users.current_org_id`.
     - `BaseProjectService.requireProjectAccess` checks **only** `project_members` when `requiredRole` is `'viewer' | 'qa' | 'developer' | 'admin' | 'owner'`.
     - Conversely, `createProject` (`project.service.ts:200`) only inserts the creator into `project_members`, so other Org `owner`s and `admin`s have no row in `project_members` and get `403` when accessing the project.
   - **Impact**: Removed/suspended organization members retain full access to projects they belonged to, including minting, rotating, and deleting live ingestion API keys (`POST /organizations/:orgId/projects/:projectId/api-keys`), while legitimate Org `owner`s and `admin`s are locked out of projects created by team members.

## 10. Recommended Fixes Ordered by Severity

### Phase P0 — Immediate Security & Tenant Isolation Hotfixes (Critical)
1. **Fix Cross-Tenant IDOR in Billing Entitlements (`pulse/src/modules/billing/entitlements/controller.ts` & `routes.ts`)**:
   - Require active organization membership (`requireOrgPermission('billing.read')` or `organization_members` `status = 'active'`) before returning entitlements for `x-org-id`.
2. **Fix Cross-Tenant SDK Config Cache Key & Membership Ordering (`pulse/src/modules/organization/sdk-config/sdk-config.service.ts:230-240` & `config/lrucashe.ts`)**:
   - Include `orgId` in `sdkConfigCacheKey(orgId, environmentId)` or verify `environmentId` belongs to `orgId` before reading from `sdkConfigCache`.
3. **Enforce Active Org Membership & Role Checks Across All `/billing/*` Endpoints (`pulse/src/modules/billing/**`)**:
   - Resolve `orgId` consistently from `x-org-id ?? req.user.currentOrgId`, verify `status = 'active'` in `organization_members`, require `billing.read` (`owner`, `admin`, `billing_manager`) for billing reads (`invoices`, `payment-methods`, `subscription`, `audit-logs`), require `billing.manage` (`owner`, `billing_manager`) for billing mutations, and restrict `POST /billing/payments/:id/refund` & `POST /billing/refunds` to `requireAdmin` (`platform_admin`).
4. **Unify `requireProjectAccess` & Cascade Org Member Removal/Suspension (`pulse/src/modules/projects/shared/base.service.ts:167-201` & `organization/members/members.repository.ts:119-133`)**:
   - In `BaseProjectService.requireProjectAccess`, **always** verify that the caller is an `active` member of `organization_members` first. Grant Org `owner` and `admin` implicit project `admin`/`owner` access even if they have no row in `project_members`.
   - When a member is removed or suspended in `MembersRepository.removeMember` / `suspendMember`, atomically deactivate/remove their `project_members` rows in that org and clear `users.current_org_id` if it matches `orgId`.
5. **Enforce Role/Permission Checks in Alerting, Observability, Errors, Event-Analytics & AI (`pulse/src/modules/{alerting,observability,errors,event-analytics,analytics,ai}` )**:
   - Block `viewer` from all `POST`/`PATCH`/`PUT`/`DELETE` mutations in `alerting/*`, `observability/errors/*`, `api/v1/errors/*`, `analytics/*`, and `automation/events`, and block `viewer` from paid LLM execution endpoints (`POST /ai/chat`, `POST /ai/analyze/*`, `POST /ai/jobs`, `POST /observability/:resource/ask`).
